## Context

The harness exists in KOTB in three layers — live machinery (`scripts/ralph*.sh`,
`until_reset.py`, `fanout*.sh`, root `Containerfile`/`Makefile`/`PROMPT.md`), the
reusable kit (`ralph-harness/`, #38), and methodology (`docs/framework/`,
`docs/ralph-loop*.md`). The kit already proved the generic-machinery vs.
answer-once-config split. This change finishes the job: the machinery leaves the
game repo for `swinney/keep-on-ralphing`, becomes a podman base image + a Claude
Code plugin, and KOTB becomes the harness's first consumer.

The hard constraint (from explore): a Claude Code plugin's files are **not mounted
into the loop container** (only the target repo is), so a plugin can never *run*
the loop. The machinery must reach the container another way — baked into the base
image. That forks the design into three channels by execution context: in-container
(base image), host-side/Claude (plugin skills), in-repo (generated config).

## Goals / Non-Goals

**Goals:**
- One GitHub-hosted source of the harness; install once, point at any project.
- Eliminate drift by making the machinery exist in exactly one place (the image).
- Keep KOTB looping throughout — it dogfoods the result as first consumer.
- Narrow, honest scope: Linux + podman, single-arch, team-shared, no directory.

**Non-Goals:**
- No multi-arch, macOS, Windows, or Docker support (stated, not implied).
- No public marketplace/directory submission.
- No registry requirement (GHCR is an optional later add, not a dependency).
- Not changing the harness's *behavior* — this relocates and re-packages the kit's
  proven surface; the runner contract is unchanged.

## Decisions

### D1: New standalone repo `swinney/keep-on-ralphing`
The harness gets its own repo so a teammate adopts it without cloning the MUD.
Layout:
```
keep-on-ralphing/
  .claude-plugin/{plugin.json, marketplace.json}   # self-hosted marketplace
  skills/{ralph-init, ralph-status}/SKILL.md
  base/{Containerfile, scripts/{ralph.sh, until_reset.py}}   # the base image
  templates/{ralph.conf.example, PROMPT.md.template, Containerfile.template, Makefile.template}
  example/                                          # golden reference
  extras/{fanout*.sh, m10-tribes.txt}               # unsupported, preserved
  docs/                                             # methodology (moved from KOTB)
  README.md
```
*Alternative — keep it in KOTB:* rejected; that is the status quo that forces a
MUD clone and breeds drift.

### D2: Base image holds the machinery; local build, no registry
`base/Containerfile` `COPY`s `ralph.sh`/`until_reset.py` to `/usr/local/bin`.
Consumers `FROM` it. Built with `make build-base` (registry-free). GHCR is a
documented additive option, never required.
*Why local build:* a Linux team already in GitHub clones the repo; building from
the canonical Dockerfile keeps the scripts-as-single-source in git and avoids
registry auth/push pipelines. *Alternative — GHCR-first:* more ops for no
near-term benefit at this team size.

### D3: Status becomes a skill, not a script
`/ralph-status` reads `.ralph/current.json` + `status.jsonl` + `STATUS.md` + git
and reports. This removes the last host-side shell script from the consumer — the
runner (in-container) is the only shell that ships.
*Alternative — keep `ralph-status.sh` in each consumer:* reintroduces a per-project
script to drift; rejected.

### D4: KOTB becomes the first consumer; machinery + methodology removed
After `keep-on-ralphing` is proven, KOTB keeps only consumer config — `ralph.conf`,
its filled `PROMPT.md`, `tasks.md`, `STATUS.md`, a thin `Containerfile`/`Makefile`
generated by `/ralph-init` — and deletes all machinery. `Containerfile.runtime` +
`compose.yaml` (game serving, unrelated) stay.

### D5: What moves vs. stays (the scoping table)
| Asset | Disposition |
|---|---|
| `scripts/ralph.sh`, `until_reset.py` | → base image (`base/scripts/`) |
| `scripts/ralph-status.sh` | → replaced by `/ralph-status` skill (deleted) |
| `scripts/fanout*.sh`, `m10-tribes.txt`, `docs/specs/fanout-harness.md` | → `extras/` (preserved, unsupported) |
| `ralph-harness/` kit | → folds into `templates/` + `base/` + `example/` |
| root `Containerfile`/`Makefile`/`PROMPT.md` (generic) | → templates; KOTB regenerates thin copies as config |
| `docs/ralph-loop.md`, `docs/framework/`, `docs/ralph-loop-evaluation.md` | → `keep-on-ralphing/docs/` |
| `docs/ralph-loop-experiment.md` (field log) | → moves too (it is the harness's evidence base); **most debatable** — see Open Questions |
| `docs/decisions/0001-container-runtime.md`, `0002-claude-auth.md` | → moves (harness rationale) |
| KOTB `ralph.conf`, filled `PROMPT.md`, `tasks.md`, `STATUS.md` | stays (consumer config) |
| `Containerfile.runtime`, `compose.yaml` | stays (game serving) |

### D6: Migration ordering never strands KOTB's loop
KOTB is loop-driven (`rpg-and-runtime-completion` pending), so the cutover is
sequenced so KOTB can always loop:
```
  1. stand up keep-on-ralphing (base + plugin + templates + example), green on its own tests
  2. /plugin install it; in KOTB run /ralph-init → generate KOTB's thin config
  3. build base; run KOTB's loop a turn or two GREEN on the new path  ← proof gate
  4. only now: delete the machinery + methodology from KOTB; rewrite CLAUDE.md §5–7
  5. update auto-memories that point at moved paths
```
No step removes KOTB's looping ability before step 3 proves the replacement.

## Risks / Trade-offs

- **Cross-repo change authored in KOTB.** Most artifacts land in the new repo. →
  Tasks label the repo for each step; the new repo gets its own tests/CI; this
  OpenSpec change tracks the KOTB-side migration + serves as the design record.
- **`/ralph-init` is non-deterministic (Claude writes files).** → The bundled
  templates + worked example are the golden reference; a post-scaffold check
  ("does it run a turn?") is the real acceptance, not byte-equality.
- **Moving the field log breaks its in-repo citations and the
  `experiment-log-upkeep` memory path.** → Update the memory; leave a KOTB pointer;
  decide the move explicitly (Open Questions).
- **Two repos drift at the docs/pointer level.** → KOTB's CLAUDE.md links out to
  `keep-on-ralphing`; the harness itself no longer drifts (one image source).
- **Team must rebuild the base after a machinery change.** → Acceptable at this
  scale; GHCR (D2) is the escape hatch if it bites.

## Migration Plan

Follow D6's ordering exactly. Each KOTB deletion is a separate, reviewable commit
*after* the proof gate (step 3). Rollback is `git revert` of the deletion commits;
since the new repo is additive and KOTB's config is regenerable, no data is at
risk. The game, its tests, and CI's quality gate are untouched throughout.

## Open Questions

- **Field-log move (D5).** Move `docs/ralph-loop-experiment.md` to
  `keep-on-ralphing` (it is the methodology's evidence), or keep it in KOTB as this
  project's retrospective with the framework citing it cross-repo? Default:
  **move it**, KOTB keeps a one-line pointer. Most debatable single call here.
- **GHCR now or later (D2).** Default: later/optional. Revisit if per-host rebuilds
  annoy the team.
- **Fan-out promotion.** `extras/` keeps fanout unsupported. Promote to a real
  capability only if a second project needs parallel fan-out. Default: leave in
  `extras/`.
- **Does KOTB's loop run inside CI or only locally?** Unchanged by this change, but
  worth confirming the new base image is what KOTB's local loop uses.
